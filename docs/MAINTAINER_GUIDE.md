# 维护与设计指南

本文保存项目的**长期规则**，面向更新数据、调整界面和维护导出逻辑的贡献者。用户首次访问请先阅读 [README](../README.md)，历史更新见 [CHANGELOG](../CHANGELOG.md)。

## 1. 模块与数据边界

| 模块 | 页面 | 数据来源 / 编辑位置 | 导出 |
| --- | --- | --- | --- |
| 销量追踪 | `index.html` | 根目录 `data.csv` | 桌面、手机 PNG；列表 JSON |
| 市场份额 | `market-share.html` | 根目录 `market-share.csv` 自动读取或本地 CSV 导入；可手动修改，浏览器本地保存 | 3:4 PNG |
| 榜单推算与出图 | `sales-estimator.html` | 导入榜单截图，读取柱长并按已知销量标定；各榜单独立计算，历史结果统一使用 `sales-estimates.csv` | 3:4 / 9:16 PNG、CSV、ZIP |

三个模块使用独立页面和数据文件：`data.csv` 是机型累计销量（万台），`market-share.csv` 是品牌周度份额（%），`sales-estimates.csv` 是指定榜单、指定周期的估算销量（台／万台）。**三者统计对象与单位不同，不自动互读、不混合汇总。** 模块 3 可手动使用同口径累计差值标定；历史估算仅代表入榜样本，不是全市场销量或份额。正式数据通过 Git 提交永久化；浏览器本地设置、自建列表和未提交编辑可能因清理网站数据、换设备或刷新而丢失。

## 2. 销量追踪 CSV 规范

`data.csv` 每行对应一条品牌＋机型记录；周列是**累计销量（万台）**，周销量通过相邻周的累计值差分得到。

```csv
brand,model,category,date,2026W34,2026W35
华为,Pura 90系列,旗舰SO,2026/5/9,128.82,134.06
```

| 字段 | 要求 |
| --- | --- |
| `brand` | 品牌，必填 |
| `model` | 机型，必填；同品牌下名称不可重复；通常不重复写品牌前缀 |
| `category` | 分类，可留空；用于悬停提示 |
| `date` | 发布日期，建议填写；支持 `2026/5/9`、`2026-05-09` |
| `2026W34` 等 | 周列，推荐携带年份；`W34` 不带年份时由 `index.html` 的 `DEFAULT_YEAR` 解释 |

维护注意：

- 新周数据在末尾追加周列，缺失单元格留空，**不要填零**；页面应显示断线而非销量归零。
- CSV 可使用 UTF-8 或 GBK，编辑前注意检查日期、单位与累计序列是否递减。
- 「我的列表」用品牌＋机型标识条目；更改 `model` 会让旧列表的引用失效，需要重新选择并更新列表。
- 页面中称为「累计销量」而非「原始值」或直接「周销量」；周增量须与累计值区分。
- 样本非全市场 TOP 榜，可能不含老款苹果、低端走量机型或定制机。旧机型退出采样不是停销，缺失也不是零销量。

### 每周更新流程

1. 从已授权公开来源核对周期与数据口径，更新 `data.csv`。
2. 检查新增列名、数量级、缺失值、累计销量异常下降。
3. 本地预览销量折线和数据表，确认品牌筛选、里程碑与手机布局正常。
4. 提交 `data.csv`；Pages 自动发布静态内容，无需每周修改 `index.html`。

公开来源主要包括微博的 **RD观测**、**数码闲聊站**；请尊重原始发布者版权并明确注明整理／估算性质。

### 完整 ISO 周生命周期（已实现）与自动对标（规划中）

完整销售周横轴和 P0 表格已上线；新机健康度 W4/W8 销量保持率、自动对标池及自动化流水线仍处于规划阶段。方法和输入输出规范参见 [《机型销量生命周期分析与自动对标规范》](SALES_LIFECYCLE_SPEC.md)。

**统一周次口径**：模块1的“完整销售第N周”和未来健康度模型均以从所填日期起的**首个完整7天ISO自然周**为W1；不足7天的上市当周称为P0，不进入完整销售周W1—W8序列，但在数据表单列展示P0天数和P0所在周末累计销量。周一上市则该周为W1。现有 `date` 字段称“发布日期”，仅当其与实际开售日期相同才可严格解释为销售生命周期；如不同，未来需增加 `sale_start_date` 并使用实际开售日。健康度自动化流水线尚未上线。

## 3. 销量追踪的交互与设计原则

以下为长期约定，调整图表时应避免无意破坏：

- **线尾标名、不使用图例**：桌面端直接在线尾显示机型；手机端使用序号与图下列表，减小横轴占用。
- **机型名称规则**：只展示同一品牌时可省略品牌；跨品牌时带品牌。以数字开头或名称不超过 3 字符（如 `15`、`600系列`、`Win`、`K90`）的机型保留品牌前缀，避免歧义。移动端溢出时优先删品牌、再截断；跨品牌选择按钮仍显示品牌。
- **默认跨品牌选择**：「全部」中每品牌取最近已更新周的最大周增量机型；优先数据更新到更近一周的记录。
- **自然周与完整销售第 N 周**：两种横轴；从所填日期起首个完整7天ISO周为W1，若所填日期是周二至周日则当周为P0并在此视图排除；周一则当周W1。未填日期的机型不显示在完整销售周视图，应提供提示。
- **两种数值模式**：累计销量与周增量；量级差大时允许使用对数轴。
- **数据表**：最新周在最左，横轴图仍按时间从早到晚。完整销售周视图中最大的 N 在左；机型和发布日期后增加 `P0天数`、`P0末累计` 两列。P0末累计是上市当周周末**累计销量（万台）**，不是P0周销量，即使切换周增量模式也保留清楚标注。周一上市P0为“不适用”；上市周历史数据缺失则P0末累计为 `—`，不能补0或推算。
- **值标签**：图中最多两位小数，手机列表取整。超过 12 条线时不画数据点，避免拥挤；重叠标签可以隐藏。
- **触屏手势**：不在图表上启用拖动或双指缩放，保证页面自然滚动；改用范围滑块与选择框。
- **本周里程碑**：以各品牌已录入的最新周为准，识别累计销量跨过 50 万台整数倍的机型，而不是要求所有品牌同步到同一周。
- **我的列表**：新增系统动态列表「近12周新机」：以CSV中**全样本最后一个有累计销量值的ISO周**为截止，自动选择该周及之前11个ISO自然周内按 `date` 上市、且有累计销量记录的机型（当前 `date` 是发布日期，后续应改用核实的开售日）；CSV更新时自动重新计算。数据载入后默认选中这份动态列表；可以直接使用原有机型勾选器增删，再点「＋ 保存当前选择」生成可长期保存的独立快照；动态列表自身不可编辑或删除，不会覆盖用户已保存的列表。若没有符合条件机型，回退到默认品牌全选。品牌切换遵循原有选择行为。
- **我的列表**：系统动态列表与自动里程碑均不可删；用户自建列表可保存、重命名、更新、删除，并可通过 JSON 导入／导出。
- **品牌色系**：小米、REDMI 橙色；华为、荣耀 红色；OPPO、一加 绿色；vivo、iQOO 蓝色；苹果 紫色。新增品牌优先检查 `BRAND_HUE`，未知品牌使用通用调色板。

### 销量追踪 PNG

| 场景 | 输出 |
| --- | --- |
| 桌面 | 16:9、2400×1350；线尾写机型名称 |
| 手机 | 4:5、1200×1500；线尾写序号，底部按最新值列机型；最多两列 12 项 |

手机网页与手机导出保持接近：网页列表可展示全部条目，导出列表有容量限制；导出图不显示数据标签。导出用不透明背景并跟随浅色／深色模式；无法标名的线用浅灰细线并注明数量。

文件名规范：`新机周销量-列表名或品牌-横轴-纵轴-桌面/手机.png`。例如 `新机周销量-华为-自然-总销量-桌面.png`；列表名中的非法文件名字符替换为 `_`。周期范围不写入文件名。

## 4. 市场份额模块

- 五种展示：双图组合、横向发散、规模比例堆叠图、坡度图、哑铃图。默认展示双图组合；哑铃图标签不附加子品牌说明。
- **规模比例堆叠**：独立堆叠图和双图组合的堆叠部分复用 `getStackMarketScale()` / `getOrderedStackItems()`。基准周大盘指数固定为 100，仅从对比周当前趋势文案（`state.w2Market`，默认由 CSV 提供）提取明确的增减方向和百分比；对比周指数 = 100 ± 变化百分数。未识别出有效方向或百分比、下降超过 100% 时按持平。两周总长度分别按各自指数除以两周最大指数缩放；各分段为本周总长度乘本品牌份额。品牌顺序统一按基准周份额降序，拆分子品牌后独立排序；不改变原始份额、不把规模指数当绝对销量。
- 默认从 `market-share.csv` 自动读取历史数据并跟随最新连续两周；手动选择较早的历史周时固定该周，选回最新一周可继续跟随未来更新。也可手动导入本地 CSV。修改份额时切换到浏览器保存的手动编辑模式；重新选择周次或点击“重载仓库 CSV”会恢复 CSV 数据，后者跳转到仓库最新周。其他按六大集团差额补足。
- CSV 表头严格推荐：`ISO 周,趋势,苹果,华为,小米,OPPO,一加,realme,vivo,iQOO,荣耀`（`vivo` 小写；解析时保留对历史 `VIVO` 的大小写兼容）。一行一周，如 `2026W45`。OPPO 列包含一加／realme，vivo 列包含 iQOO；拆分时主品牌 = 集团 − 子品牌，禁止重复加总。必须提供全字段，校验各项在 0–100%、子品牌不大于集团、六大集团合计不超过 100%。
- 仓库 CSV 读取失败时，仍保留本地保存的配置或内置 W44/W45 示例；该示例不是官方统计。更新 CSV 后无需修改 HTML。主副标题、周标签与洞察的手动覆盖可保留；趋势描述不适用跨周覆盖。点击“恢复所选周 CSV 原始数据”可撤销自动字段的手动覆盖。
- 六套主题：柔雾丁香、**编辑部米白（模块2与3统一默认）**、极简纯白、雾蓝极简、日落珊瑚、莫兰迪绿野。已选择过主题的浏览器仍优先使用本地保存的选项。
- 网页输入区保持浅色卡片；海报有独立主题。SVG 绘制后按所选分辨率经 Canvas 导出 3:4 PNG；尺寸与共同规范见第 6 节。
- 顶部趋势双卡每次切换所选周次时，直接从对应 CSV 行的 `趋势` 列生成 `大盘趋势：<趋势>`，不受历史手动文案覆盖标记影响；当前周可临时手动修改，但下次切换周次会恢复 CSV 描述。趋势卡文字使用中性主文字色，避免无条件表示上涨。品牌份额变化以百分点（pp）表示，而不是份额相对涨跌幅。主副标题、洞察和底部水印文案可手动编辑，原有覆盖规则保持不变。
- 抖音右侧交互区／底部文案区是独立安全边界；预览参考线不应进入导出图。

## 5. 榜单推算模块

### 历史销量 CSV

- `sales-estimates.csv` 为唯一正式历史明细，固定英文表头，一行一个榜单条目。`dataset_id` 由来源、榜单系列、周期类型、规范化周期组成（各部分保留中文等原始文字，用 `|` 连接，仅转义字段内部的 `%` 与 `|`），排名在榜单内唯一。开发阶段不支持早期整段 URL 编码的旧 ID，也不自动迁移；旧开发数据应重新导出。TOP 数不参与 ID；`top_n` 是可选标称规模，`actual_count` 为真实条目数。25 条可记 TOP25，也可在原榜 TOP30 时记实际 25 条；标称规模须为不小于实收数的正整数；未知规模留空，不补零。
- 标准 CSV 表头（顺序固定）：

```csv
dataset_id,source,series,period_type,period,period_start,period_end,top_n,actual_count,rank,model,brand_group,pixels,estimated_units,estimated_wan,fit_k,fit_mode,calibration_count,accepted_count,outlier_threshold,algorithm_version,saved_at
```

- `period_type` 支持 `weekly`（ISO 周）、`monthly`（自然月）、`custom`（起止日期）。同周期若存在来源相同但口径不同的榜单，应填写不同的 `series`。品牌系列沿用 `safeBrand()` 的合并口径，机型字段保留榜单原始名称；合并行不可拆分。
- `estimated_units` 为四舍五入后的整数台数，`estimated_wan` 为该整数换算的四位小数，`fit_k` 保留计算精度；`fit_mode`、标定组数、有效组数、异常阈值、算法版本、保存时间随结果归档。仅 `single`、`fit`、`robust` 且补全机型名称的有效估算可进入正式 CSV；单组及剔除异常组的结果仍须人工核验。
- **读取与导出校验**：标准 CSV 使用 UTF-8（导出含 BOM）；表头、列数、合法周期、ID、排名唯一性、实际条目数与组内元数据必须一致。台数须等于 `Math.round(fit_k * pixels)`，万台值须在数值上等于台数除以 10000。允许起止日期为 `YYYY/M/D` 或 ISO 日期，以及万台小数省略末尾零；读取后规范化为 `YYYY-MM-DD` 和四位小数。不能为了容忍表格软件格式变化而放松实际数值和周期校验。一条非法记录会阻止整份新历史载入，提示异常记录或榜单；不会静默丢弃行。
- 页面加载仓库 CSV，刷新按钮以时间戳和 `no-store` 请求重新读取；读取失败时须成功重试或确认导入完整历史文件后才能合并导出，不能将失败当作空数据库。已加载的记录在刷新失败时可继续显示，但不得视为最新仓库数据。合并导出会保留其他周期，遇同 ID 数据变化须用户确认整期替换（旧版由 Git 提交历史保留）。同一会话的多次合并保留在内存，刷新前请下载备份；点击“刷新仓库历史”时若有未提交记录，必须先确认替换当前会话数据；如仓库被其他设备更新，应重新加载最新历史并导入未提交文件，再合并导出。GitHub Pages 不写回仓库，由维护者提交下载的完整 `sales-estimates.csv`。
- 本期标准销量 CSV 与历史文件表头相同，可导入合并；原标定报告、机型派生分析和品牌分析 CSV 保留作人工参考，不作为历史明细导入。发布 ZIP 增加本期标准销量 CSV。历史列表只读，不恢复截图、标定组原始输入或未完成草稿；选择历史榜单即同步图文工作台，也可点击“使用所选历史榜单生成图文”直接跳转。工作台沿用存档销量、品牌系列、柱长、标定状态及组数，四类图卡、文案、派生 CSV 与 ZIP 均用所选数据；历史 ZIP 的标准销量 CSV 保留已载入、规范化后的存档字段和原保存时间，不重算或补造标定组。点击“切回当前标定榜单”或成功导入新榜单截图，恢复当前标定工作流。历史数据不进入上方截图编辑器，不需要也不能在历史模式补造标定组。
- 实现在 `sales-estimate-archive.js`，周期计算复用 `iso-sales-week.js`。不要在前端保存仓库写入 Token，不要把缺榜条目当作零销量或把周榜与月榜累加。

### 标定与出图

- **估算销量展示精度**：前台结果表、历史榜单、数据概览、四类 Canvas 图卡以及自动生成的分析文案统一使用 `displayWan()` / `displaySale()`，以万台为单位保留一位小数。销量差值和品牌合计先用原始精度计算再格式化；拟合计算、排名、柱长比例、已知标定输入及所有 CSV 原有精度不变。样本占比、销量倍数按各自格式展示。
- **单一截图入口**：页面默认打开空白标定编辑器，不内嵌 Base64 截图、预设榜单或测试柱长，不提供原图预览区域。左侧“导入新榜单截图”支持 PNG／JPG／WebP 白底、蓝色水平柱条榜单；当前识别算法接受 2–100 条柱条（无需固定 TOP30／TOP40）。图像仅在浏览器临时解码和测量，完成后释放 Object URL，只保留柱长等测量数据，不保存或上传图片。导入新图时重置标定、选择及周期元数据；已归档榜单从历史 CSV 选择。
- **机型名称录入**：按识别榜单的原排名逐行填写；忽略末尾空行，保留中间空行的行号且不覆盖该行旧名称。提示行数不符、未填写、超范围、缺失名称及未知品牌；刷新双机 PK 选项。未知品牌不可强行归并，品牌图卡和整套 ZIP 须先补全可识别品牌名称。
- 由柱长像素确定相对比例；必须输入**同统计期、同口径**的销量才能推算绝对量。
- 支持单机已知销量及最多五机合计标定，接受累计销量差值表达式，如 `782.87-689.03`。多组标定不一致时提示异常，避免给出不可信的绝对量。
- 品牌系列统计按当前**入榜样本**合并：小米＋REDMI、OPPO＋一加、vivo＋iQOO；苹果、华为、荣耀独立。展示条目数、样本合计和主力机型，不是全市场份额。
- 四种图卡：TOP10、双机销量 PK、品牌上榜实力、榜首领先。支持六套主题、文案编辑、3:4／9:16 两种比例、PNG／CSV／ZIP；分辨率见第 6 节。
- **榜单标签**：主视觉文案编辑区在副标题之后、账号水印之前提供 `copyTagLabel`。历史默认采用周期与 TOP 规模的规范短名（实收不足时标示实际条数），新截图默认取文件名去掉 PNG／JPG／JPEG／WebP 后缀，未导入时为空。标签属于展示层，不修改 CSV 周期、ID、文件名或统计口径；切换数据源时恢复相应默认值，切换模板／主题／比例时保留手动内容，清空则隐藏标签，恢复默认文案按钮可重置。四类图卡的预览、PNG 和 ZIP 共用 `getPosterCopy()` / `posterFrame()`；长文字限制宽度，背景适应文字长度。
- 双机 PK 机型名优先单行，必要时去除品牌前缀再自适应字号；销量数字保留光学左对齐处理。
- 桌面端工作台左侧独立滚动，右侧预览保持可见；窄屏改成上下布局。
- 右侧与底部安全区独立调节；底部免责附注在安全线附近独立定位，避免额外空白。品牌图卡的“系列归并”固定说明位于免责附注横线正上方，由 `drawPosterFooter()` 与 `posterFooterGeometry()` 独立定位，随底部安全区整体移动并限制在右侧安全边界内，不随主体缩放，也不受自定义免责文字清空影响；品牌主体布局须为该说明及页脚预留空间。

## 6. 统一图卡与水印规范（模块 2 / 3）

- 操作界面统一为浅灰／白底、浅色边框、蓝色交互强调，右侧安全区红色、底部安全区橙色。
- **单一主题来源**：`poster-themes.js` 是模块2（SVG）和模块3（Canvas）的六套海报主题唯一数据源。不要在页面内复制第二套主题字面量、固定背景或静态色卡。
- **共同层级**：主题渐变外底（`bgTop` → `bgBottom`）→ 白色圆角主卡片（`#fff`＋主题色边框）→ 白色图表／数据内卡（同主题边框）→ 低透明度主题色的重点行。两模块主卡留边、圆角、点阵密度统一读取 `PosterThemes.layout`。页面操作区仍使用独立的浅灰白卡片式 CSS，不随海报主题变化。
- **主题颜色语义**：`upColor` = 主强调色／份额上升；`downColor` = 辅助强调色／份额下降；`textPrimary`、`textSecondary`、`textMuted` 构成文字层级；`cardBorder`、`gridLine` 分别负责容器边框和中性数据底轨。模块3的榜首用主题主色、其他机型用辅助色，**不应把“排名落后”解读为负增长**。
- **品牌识别色独立**：模块2份额堆叠使用各品牌固定识别色，不能为了套用主题而改掉苹果、华为、小米等品牌的标识颜色。
- **维护纪律**：新增海报主题先改 `poster-themes.js` 的语义色；模块2／3色卡从该脚本读取主题色。涉及 SVG／Canvas 海报渲染、主题语义或导出代码的修改才做对应主题、比例和 PNG／ZIP 的针对性验收；仅修改操作台 CSS 不要求全面导出测试。
- **字体与字号**：模块 2／3 的网页操作台只保留 **4 档字号**：12px（辅助说明）、14px（正文、表格及输入控件）、16px（普通章节和面板标题）、24px（重点指标、大型分区标题及页面主标题）。旧 11px 并入 12px；旧 20px 根据用途归入 16px 或 24px。没有明确的信息层级差异，不得为了装饰或微调增加新字号，优先调整字重、颜色及间距。只在**独立纯数值字段**使用 IBM Plex Mono，包括数字输入、排行、销量与比例；中文标题、列名、选项、日期及数字与中文混排的说明（例如“3:4 竖屏比例”“15%（推荐）”）使用中文无衬线正文字体，不要因其中存在数字而给整个元素添加 `font-mono`。网页操作台的字号规范不覆盖 SVG／Canvas 海报内部独立字号与排版。字体从网络加载失败时回退系统字体；Canvas 单独数字做字形左边界修正。
- **共享操作台 CSS（单一来源）**：模块2、3均以 `<link rel="stylesheet" href="studio-ui.css">` 加载 `studio-ui.css`。它统一 4 个 `--ui-text-*` 字号变量、字体栈、颜色、间距和 `.ui-panel`／`.ui-section-title`／`.ui-field`／`.ui-palette-grid`／`.ui-palette-card`／`.ui-swatches`／`.ui-watermark-card` 等控件。添加相同功能的控件，先复用 `ui-*` 类，不在模块内部重新写同名色卡／水印 CSS；模块特有布局可保留在各自 HTML。
- **操作台字体统一（全控件）**：`studio-ui.css` 中 `--ui-font-body` 采用系统 UI 字体栈，模块2／3的标题、英文标识、按钮、表单、表格、说明、色卡和水印设置均使用它；首页顶部导航也引用该变量，但首页 ECharts 继续使用原有 `--f-body` 做文本测量和导出，不能改动。独立纯数值使用 `--ui-font-number`（IBM Plex Mono）。模块2加载的 Noto Sans SC 等网络字体仅用于有独立字体规则的 SVG/海报；模块3 Canvas 海报文字同样独立，不因操作台字体统一而改动。操作台 CSS 字重使用 400／500／600／700／800，避免 650／750／780／850 等额外字重。页面主标题统一为 24px、800 字重，较长标题允许窄屏换行。
- **维护边界**：`studio-ui.css` 管理模块 2／3 共用的操作台组件；`market-share.css` 管理模块 2 特有的控制台布局、数据编辑表格、开关和安全区模拟层。模块 2 已移除 Tailwind CDN 和工具类，不再新增 Tailwind 或复制一套原子工具类；优先为真实控件设置简明的语义 CSS 类。两份 CSS 均不覆盖海报 SVG、Canvas、`poster-themes.js` 或第三方 ECharts。模块3主题按钮在 `syncPaletteChooser()` 中切换 `is-selected`，模块2在 `renderPaletteButtons()` 中设置该类与 `aria-pressed`。
- **界面简化原则**：以排列整齐、数据清楚、功能正常为目标；不为简单操作界面新增渐变、复杂阴影、动画或装饰性控件。图表预览的安全区模拟层仅作辅助显示，导出 PNG 使用独立 SVG 克隆与 Canvas 序列化，不依赖 Tailwind 样式。
- **轻量防回退检查**：修改共享样式或控件 HTML 时运行 `node --test tests/studio-ui-style.test.cjs`，同时只检查两模块主题色卡和相关水印卡片在常见桌面／窄屏下的溢出与间距。静态检查不能替代实际页面视觉验收。

- **图片水印**：全屏倾斜（默认关闭，`归零return0`，透明度 8%，字号 32px，间距 220px）与中心单个（默认关闭，同文案，透明度 12%，字号 72px）互斥。模块 3 左上角账号默认同为 `归零return0`，与数据来源说明分离，不因账号名称修改而更换原始数据归属。水印覆盖图卡可用内容区域，预览及 PNG 一致；模块 3 的四图 ZIP 一样会带水印。
- 水印设置保存在浏览器；第二模块使用原有页面状态，第三模块使用独立键。清空自定义文案不应自动恢复默认文字。
- 导出时不包含用于辅助定位的抖音安全线或交互区遮挡模拟层。

### 出图比例与 PNG 分辨率

模块 2 固定 3:4，模块 3 支持 3:4 与 9:16；两者统一四档导出宽度。分辨率只改变最终像素数，不改变预览尺寸、图卡排版、主题和安全区比例。模块 3 单图和 ZIP 使用相同选择；极清档需要更多内存。

| 档位 | 3:4（模块 2 / 3） | 9:16（模块 3） |
| --- | --- | --- |
| 标准 | 1080×1440 | 1080×1920 |
| 高清 | 1620×2160 | 1620×2880 |
| 超清（默认） | 2160×2880 | 2160×3840 |
| 极清 | 3240×4320 | 3240×5760 |

模块 2 从 SVG 逻辑画布按目标尺寸栅格化；模块 3 从 1080 宽的逻辑画布按像素倍率直接渲染，避免对低分辨率预览截图放大；安全区参考线仅用于预览。模块 1 的桌面／手机输出仍遵循第 3 节，不使用以上四档。

## 7. 技术与部署

- **静态页面**：`index.html`、`market-share.html`、`sales-estimator.html`；模块2／3还需部署共享文件 `studio-ui.css`；模块1／3必须加载共享日期脚本 `iso-sales-week.js`（提供浏览器 `IsoSalesWeek` 全局及 Node CommonJS 导出）；模块2/3共用主题脚本 `poster-themes.js`；模块2额外加载 `market-share.css`、`market-share-data.js` 与 `market-share-import.js`，并复用 `iso-sales-week.js`。无后端或打包步骤。模块3额外加载 `sales-estimate-archive.js` 并读取 `sales-estimates.csv`。部署须包含这些脚本和数据文件。ISO周计算禁止在新模块中复制另一套实现。使用 `node --test tests/iso-sales-week.test.cjs` 运行日期边界测试。
- **依赖**：销量追踪使用 Apache ECharts 5.4.3（cdnjs）；市场份额编辑器使用原生 HTML/CSS 与 SVG，不依赖 Tailwind；模块 3 使用 Canvas 图卡导出。字体仍使用 Google Fonts，失败时回退系统字体。完整离线部署仍需考虑 ECharts CDN 和字体资源。
- **本地预览**：项目根目录执行 `python3 -m http.server 8000`，浏览器访问 `http://localhost:8000`；直接打开 HTML 可能触发 CSV 的本地文件访问限制。
- **GitHub Pages**：Settings → Pages → `Deploy from a branch` → `master` → `/(root)`。
- **直达链接**：`/` 为销量追踪，`/#market-share` 为模块 2，`/#sales-estimator` 为模块 3。
- **公开性**：GitHub Pages 和仓库公开；不要将私人或未经授权的数据提交到任何数据 CSV 或截图目录。在发布估算图卡前核对来源与统计口径。


### Cloudflare 分模块部署

- 原有根目录源码与 CSV 仍是维护源；Cloudflare 构建通过 `scripts/build-cloudflare.mjs` 的明确白名单生成 `dist/`。只有模块 1 的首页、数据及共享依赖公开；模块 2／3 及其独立 CSV 放在 `/studio/`。不发布 README、维护文档、测试和 Git 历史。
- `wrangler.jsonc` 固定静态资产目录并禁用预览 URL；`cloudflare-worker.mjs` 对私有路径和登录／会话入口校验 Cloudflare Access JWT，缺少配置或验证失败即拒绝访问。必须保留服务端权限校验；首页 hash、iframe 显隐、本地存储或账号名称不是权限依据。
- 邮箱白名单由 Access 的 Allow 策略管理，`CF_ACCESS_TEAM_DOMAIN` 与 `CF_ACCESS_AUD` 在 Cloudflare Worker 控制台设置；不要提交令牌及邮箱名单。未完成配置及旧公开部署清理前不能宣称数据已私有。
- Cloudflare 部署使用 Node/npm（仅部署侧依赖），业务前端保持原生静态 HTML/CSS/JS；本地根目录预览不需要构建。实际设置、旧部署保护及手动验收见 [Cloudflare 部署指南](CLOUDFLARE_DEPLOYMENT.md)。

## 8. 开发与测试流程（轻量优先）

- **默认原则**：优先完成用户明确要求的功能，并验证核心流程能跑通；严格控制改动范围，不因简单需求主动扩大为全面重构、全量回归或额外功能开发。
- **最小验收**：根据改动性质选择针对性检查。数据导入类改动，优先验证实际 CSV 加载、字段映射、关键异常输入、周次切换及被直接影响的原有功能；已有相关单元测试可运行，但不应为追求测试数量增加低价值用例。
- **按风险升级**：涉及统计口径、核心计算、共享组件、数据丢失风险或较大范围重构时，增加必要的边界与回归测试。涉及主题、布局、导出等视觉改动时，只针对受影响部分验收；不影响这些部分的改动，不默认执行六套主题、全尺寸图片或 PNG/ZIP 的全面验收。
- **用户决定范围**：用户明确提出“先跑通流程”“不要求数字完全对应”“导出由我自己测试”等要求时，以此确定交付和测试边界；未执行的验收如实说明，不把模拟交互等同于完整页面实测。
- **提交效率**：先集中实施并完成必要检查，优先以少量有意义的提交提交 GitHub；避免为了轻微修正反复提交、重复获取相同信息或进行无关检查。没有必要时不创建多轮 PR/提交。
- **透明记录**：区分代码开发、测试执行、工具交互与等待耗时；没有独立计时记录时，不将 GitHub 提交时间跨度或整个处理过程解释成“测试耗时”。
